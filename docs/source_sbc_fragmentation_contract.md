# Bounded A2DP Source SBC fragmentation

The player supports its existing stereo, 16-block, 8-subband, loudness SBC format, bitpool 2–53, at 44.1/48 kHz. When a complete frame fits, the existing one-to-four-frame batching remains unchanged. Otherwise it sends exactly one encoded frame in 2–15 fragments. The payload limit includes the SBC header and excludes RTP. Each fragment carries up to `payload - 1` encoded bytes. A limit requiring more than 15 fragments, or leaving no encoded byte, is rejected before PCM input. This is a bounded library capability, not a claim that every synthetic payload size is a valid negotiated L2CAP MTU.

## Wire grounding

Bluetooth SIG [A2DP 1.4.1 §§4.3.3–4.3.4](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/a2dp_v1-4-1_1752513648/A2DP_v1.4.1/out/en/index-en.html) requires integral complete frames when they fit; otherwise basic, nonmultiplexed transport uses fragmentation. Fragment packets share a timestamp and nonfinal packet sizes. F identifies fragmentation, S/L identify first/last, and the low nibble counts remaining fragments including the current packet. M/X are zero; PT is dynamic. [RFC 3550 §5.1](https://www.rfc-editor.org/rfc/rfc3550.html#section-5.1) specifies per-packet sequence advancement. The sender sets reserved bits to zero.

The installed BTstack is `501e6d2b86e6c92bfb9c390bcf55709938e25ac1`. Its raw media packet API delegates to `l2cap_send`; the basic classic path checks live credit before reserving/copying. The payload-RTP helper advances its SDK sequence before send, so it is not used. Retry safety remains limited to the CYW43 polling/basic AVDTP path, not ERTM or arbitrary asynchronous ports.

## Ownership and progress

- The player explicitly enables fragmentation on its private transport. Other transport users retain the disabled default. Boolean `send()` never sends a partial prefix, even if fragmentation is enabled; progressive consumers use `sendResult()`.
- `Progress` is appended to `ITransport::SendResult` and `AudioPipeline::Result`; existing enum values are unchanged. It reports one accepted physical packet with an incomplete media batch. `Deferred` means this call accepted no bytes. Both retain the exact batch. No re-encoding or rereading PCM occurs between fragments/retries.
- The transport owns a fixed 118-byte snapshot plus scalar length/offset. Changed retry bytes fail before another SDK call. No pumping allocation is added. Existing 1024-byte transport storage and 1036-byte RTP packet vector remain. A fragmented pipeline batch has 256 interleaved samples, 118 encoded bytes maximum, and the pipeline's existing extra PCM allocation factor. Complete-frame maximum remains four frames. Configuration may transiently hold old and replacement allocations.
- `MediaProgress` increments reducer physical packets only. Final `MediaResult` increments physical packets and completed media batches, then advances accepted samples and rational pacing once (128 samples for a fragmented frame). RTP sequence advances per successful packet; RTP timestamp advances on final completion. Busy changes neither. Every packet still requires a later poll and fresh credit; no send loop is introduced.
- Public `sent_packets` and snapshot `packets` count physical packets. Appended `completed_media` counts completed batches, not necessarily individual codec frames. `media_deferrals` excludes successful fragment progress. Appended `abandoned_partial_frames` counts each discarded group with at least one accepted nonfinal fragment; an unsent Busy batch does not count. Repeated reset cannot count the same group twice.
- Pause, pipeline reset, accepted codec reconfiguration and disconnect discard pending PCM/encoded/fragment state. Same-session pause/reset/codec reconfiguration preserve accepted RTP sequence/timestamp. A new-session transport `configure()` retains its existing behavior of resetting sequence/timestamp to zero. Abandoned incomplete media never earns accepted samples or pacing credit.
- `abandonPending()` invalidates the transport generation as well as fragment ownership. An outstanding send returning through a synchronous reset cannot resurrect stale offsets. A generation-changed completion returns Failed without applying sequence/counters/offsets to the new state, including a synthetic SDK SUCCESS. The supported basic path has no send-internal callback/yield; physical counter attribution is not guaranteed for such synthetic obsolete completions or arbitrary asynchronous ports. Captured SUCCESS is not evidence of zero physical transmission. The generic pipeline calls the old transport hook before replacement only when encoded bytes remain pending. That pending owner must stay alive until replacement finishes. With no pending batch, configure never touches the old transport, so a completed stack transport may have been destroyed. Failed results abandon retained transport state before pending bytes become zero. Reset/loop still require their currently borrowed objects to be alive. The hook defaults to no-op for existing transports. Configure remains prohibited while pumping.

New enum/state/diagnostic fields require recompilation; no binary ABI compatibility is promised. No Sink, shared-peer policy, security/admission, codec envelope or generic lifecycle expansion is included.

Host assertions and offline ARM linking are not radio, peer-interoperability or hardware acceptance.
