# Explicit, measured A2DP Sink delay reports

[日本語](README_jp.md) | [Public API contract](../../docs/a2dp_sink_pcm.md#explicit-delay-reporting-host-verified-hardware-acceptance-open)

This is a complete **application command path** to
`A2dpSinkReceiver::reportDelay100us`, not an audio-latency meter. A bounded input
line is parsed on the main loop after `receiver.poll()`, checked against its
original measurement context, and attempted once. No reports are generated by
polling, incoming PCM, connection events or retries.

## What you must supply

`UnconnectedOutput` has **no renderer, DAC or I2S output**. It returns zero accepted
frames so the receiver honestly counts the PCM as dropped. It neither records
nor plays audio, and cannot produce a receive-to-render latency measurement.
Replace it with your actual bounded output pipeline before reporting that
pipeline's measured delay. See the [PCM consumer guidance](../../docs/a2dp_sink_pcm.md).

Measure the actual total latency relevant to your pipeline, including decoder,
queued PCM and output-device/render delay as applicable. FIFO occupancy, a frame
counter, a guessed constant or this sample's processing time is not that
measurement. The sample cannot verify a supplied number's physical accuracy.
Do not report a value for a different pipeline or a disconnected/previous stream.

Capture the receiver generation AND `OutputBoundary::epoch()` when starting the
measurement. Preserve those tokens with the completed measurement and check
them again when the measurement finishes. If either changes, discard the
measurement. Every output `reset()` invalidates the epoch, including stop/start
or format changes that keep the same receiver generation. Real output code must
also reset the boundary when its own output timing/configuration changes.
Neither token is an age deadline: the application must decide when a measurement
has become too old even without a stream boundary.

## Build safety and configuration

The default has radio **OFF**, an **empty peer**, and returns before stdio,
receiver construction or Bluetooth initialization. It remains type-checked.
The enabled path still waits for an explicit `begin` command. Pairing confirmation
is always false. There is no automatic discovery, connection, reconnect, new
persistent bond storage or report. A source requiring new pairing confirmation
will need a separately reviewed application pairing policy.

From the repository root, with an installed Pico SDK/toolchain and local
picotool metadata (SDK 2.1.1 was used for the evidence):

```sh
export PICO_SDK_PATH=/path/to/installed/pico-sdk
cmake -S examples/A2dpSinkDelayReportSample -B build/sink-delay-default \
  -DPICO_SDK_FETCH_FROM_GIT=OFF -DFETCHCONTENT_FULLY_DISCONNECTED=ON \
  -DFETCHCONTENT_UPDATES_DISCONNECTED=ON -DPICOTOOL_FORCE_FETCH_FROM_GIT=OFF \
  -Dpicotool_DIR=/path/to/installed/picotool/cmake
cmake --build build/sink-delay-default --parallel 2
```

To **compile** the command path, use a separate build directory and add
`-DSINK_DELAY_ENABLE_RADIO=ON -DSINK_DELAY_PEER="YOUR_SOURCE_ADDRESS"`, replacing
the peer with the exact authorized source's six hexadecimal octets. Empty, zero,
broadcast or malformed enabled addresses are rejected at configuration time.
Building does not flash or run the firmware. The evidence uses a clearly
fictional compile-only peer; never run that firmware against a device.

## Commands after flashing your Pico W

Each command is an entire ASCII line ending in LF or CRLF, without leading or
trailing spaces. Commands are case-sensitive.

1. `begin`: attempt initialization once for the process lifetime. A failure is
   terminal; receiver and output stay alive and polling continues.
2. `status`: wait for `working=1` and no failure. Then use `listen` for the exact
   peer's incoming connection, OR `connect` for one outgoing attempt.
   Local acceptance does not mean connected or streaming.
3. `status`: reports generation, output epoch, eligibility and lifecycle flags.
   This example requires active streaming, stricter than the public API's
   stable CONFIGURED/OPENED/STREAMING states. Capture tokens with the real
   measurement, not by looking up a newer generation at send time.
4. Submit `report <id> <measurement_generation> <measurement_output_epoch> <actual_measured_us>`.
   Angle-bracket names are placeholders, not literal command syntax. Each field
   is an unsigned decimal integer in 0..UINT32_MAX. IDs/generation/epochs must be
   nonzero. Measured microseconds must be 0..6553500, inclusive. Real measured
   zero is valid; zero does not mean "unknown". Upward rounding is `(us+99)/100`
   only AFTER range checking, with no overflow or clamping.
5. `disconnect` requests closure and invalidates the output epoch. Keep polling
   until closure is visible. Reconnect is a separate explicit command; obtain a
   NEW measurement with its new generation/epoch. `stop` disconnects and
   permanently disables begin/listen/connect/report for this process.
   `status` remains available. Receiver failure also stops the workflow.

The input has one partial-line slot, no application command/report queue, a
64-byte line limit (excluding LF, including optional CR) and at most 32 input
reads plus one completed command per loop. Excess bytes, binary/control input,
malformed/overflowed numbers, incomplete fields or extra tokens never send.
Overlong/bad lines drain to LF; their prefixes/tails are never interpreted as
commands. An incomplete line is held without reporting until LF. A partial
report crossing a generation/output-epoch/readiness boundary is rejected.
Complete lines still buffered by the transport are independently checked when
read; old tokens cannot be relabeled after reconnect/reset.

Use increasing IDs for the entire firmware process, starting at 1 or greater.
Once a syntactically valid report with a new nonzero ID is submitted, the ID is
consumed **before** any lifecycle/range/API result, including busy. That ID and
all smaller IDs can never submit again. Malformed lines and ID zero consume no
ID. UINT32_MAX can be used once; there is no ID wrap or reset. Epoch overflow
permanently invalidates measurements. Reentry consumes no input and cannot make
a nested API call. Control commands have no report ID and do not change it.

IDs and epochs are **process-local**. They are not persistent replay protection
and do not establish measurement freshness across reboot. Flush external command
buffers when restarting; never replay saved measurement commands into a new
process. This protocol does not authenticate the sender or detect arbitrary
transport byte loss/corruption that accidentally forms another valid command.
Use a reviewed authenticated/framed transport if your application requires that.

## Interpret results correctly

Local parser/lifecycle rejection means **no API attempt**. `attempted-once`
means the public API was called, not necessarily that BTstack was called.
The reported API status is one of:

- `Accepted-local-SDK-admission-only`: local SDK admission/queuing only. No
  delivery, remote ACK, rendered-output or latency compensation is established.
- `InvalidDelay`, `StaleSession`, `NotReady`, `NotNegotiated`: the public API
  rejected the request. Its deeper ownership, live ACL/endpoint, pending-event
  and negotiated-support guards remain authoritative.
- `SdkRejected-no-retry`: exact SDK byte status is printed, including busy.
  This is not success and is never retried automatically.

SDK status is printed only for Accepted/SdkRejected. Every decision is one-shot.
If a further attempt is appropriate, first inspect the state and obtain an
appropriate current measurement, then submit an explicit NEW ID. Do not turn
busy into blind periodic retries or reuse/retag a measurement across boundaries.

Output callbacks only account for/reset output state. They do not parse commands,
log, call receiver methods or measure/report delay. All receiver/report operations
remain on one main loop, outside all callbacks, IRQs and a second core. USB output
is configured with a zero wait timeout and may drop logs; a missing log is not
permission to retransmit. Bounded input work is **not a measured wall-clock or
real-time polling guarantee**: stdio, library work and a replacement output
pipeline still need timing analysis.

## Tests and limits

```sh
bash tests/host/run_sink_delay_use_flow_tests.sh
```

Host checks use modeled reporters to test input, unit conversion, session boundaries, duplicate rejection and no-retry behavior. Hardware execution is **NOT_RUN**. These checks do not establish measurement accuracy, peer delivery, delay compensation or device compatibility. See the [Validation scope](../../docs/validation.md).
